# 03.2 — FM representation research

## Goal

Determine, empirically, how FM20 stores and presents manager knowledge.

Research both whether an entity is discoverable and which fields are visible
for that entity. These are separate questions.

## Attribute-visibility status snapshot — 13 September 2026

The detailed chronological log below is preserved as the evidence trail. This
section is a rollup for anyone who needs the current state without reading
the whole history.

**What's proven and working.** FM's own visible-result builder (module RVA
`0x15A4A90`) can be called directly against the live FM process, for any
loaded player and any supported attribute, without opening a screen, and
returns exactly the two-byte exact/range/unknown result FM's UI would show.
It never reads the concealed third byte the same structure carries. This has
been validated to 0 mismatches across 97 attribute checks spanning three
players with deliberately different knowledge profiles (a heavily-scouted
defender, a completely unscouted striker, and a goalkeeper), then
corroborated further against an owned squad player (guaranteed-exact
attributes), a world-class reputation player (a mix of exact and ranged
results), and a fresh random player, all matching expectation. It has
survived three separate FM process restarts and one full save reload.

**The one real bug found, and its fix.** A systematic check against real FM
attribute exports found 11 false positives (a fabricated visible range where
FM's own UI showed nothing) concentrated on specific attributes on specific
players. The cause, found via a passive hook recording FM's own real
arguments to the builder: both cold-call tools fabricated a caller-context
struct's first 8 bytes as the manager's pointer, but FM's real calls always
pass zero there. Fixing that eliminated every false positive with no
regressions. See "False-positive root cause found and fixed" below for the
full evidence trail.

**Tooling.** `fm20_cold_visibility_call.py` / `.gdb` (GDB-scripted native
call) and `fm20_cold_visibility_ptrace.py` (raw Linux `ptrace`, no GDB
dependency) are the two independent, cross-validating call mechanisms.
`fm20_builder_call_arguments.py` passively records FM's real builder
arguments without ever calling into FM -- the tool that found the bug above.
`fm20_player_visibility_query.py` formalizes a reusable "look up this
player's full visible attribute profile by name or ID" entry point on top of
the proven call mechanism.

**Coverage gap, not a bug.** `punching`, `eccentricity`, `freeKickTaking`,
`penaltyTaking`, and `longThrows` have no raw offset or display ID anywhere
in the codebase -- never reverse-engineered, discovered when a goalkeeper's
real export showed a Punching value no tool could query. Closing this needs
the same offset-plus-display-ID-plus-real-export validation as everything
else, not a plausible guess.

**Open questions, documented but not blocking.** A second, call-varying
7-byte field inside the same caller-context struct is still fabricated as
zero; it produced zero mismatches across all 97 checks, which is evidence it
isn't load-bearing for the exact/range/unknown decision but is not proof it
never matters. Every real builder call captured so far had a null optional
report-object argument; its behaviour when genuinely non-null has never been
observed.

**What this explicitly is not.** A production data source. There is no
discoverability gate anywhere in this codebase: every tool here trusts a
supplied player ID or resolves a name by scanning every loaded player in
process memory, which is not proof a real manager could ever encounter that
player through FM's UI. Nothing here is wired into `FmDataSource`, the HTTP
bridge, or the recruitment analytics. That gap is the subject of the
discoverability investigation now underway (see the phase README's Current
status for its plan and progress).

## Test matrix

Use controlled players representing:

- our first-team and youth players;
- a highly known league opponent;
- a fully scouted transfer target;
- a partially scouted target with ranges;
- an unscouted player;
- a player whose report has become stale;
- a trialist or newly signed player where knowledge changes quickly.

Also capture controlled player-search result sets with known filters and no
filters where the UI permits it. Compare counts, stable IDs, pagination, and
membership before and after scouting, staff/knowledge changes, and save reloads.

For each, record the visible UI, source structures accessed, bridge candidate
mapping, in-game date, manager/scout setup, and changes after additional
scouting.

## Guardrails

- Raw hidden values may be inspected only during an isolated research process
  if absolutely required to identify the correct visible structure; they must
  never be logged, fixture-recorded, persisted, or exposed by production code.
- Prefer proving the manager-knowledge source directly over comparing against
  underlying truth.
- Never treat enumeration of the internal player database as player-search
  visibility. The production query must start from a verified discoverability
  or manager-knowledge structure.
- Use invented/sanitized examples in repository documentation.

## Historical UI-export validation path (not a production dependency)

FM's player tables provide a safer near-term source because the game can export
the currently displayed Squad, Shortlist, or Player Search view as a web page.
An [FM20-era analytics workflow](https://community.sports-interactive.com/forums/topic/545140-fm-data-analytics-a-data-visualization-tool-based-on-r-shiny-v3-released/)
documents using `Ctrl+P`, selecting Web Page/HTML, and importing both squad and
shortlist outputs. It also records two completeness hazards: large lists may
need scrolling before export, and the workflow observed a 500-player limit.

The first strict Python parser was implemented as a validation fallback. It accepts a
table only when it contains `UID`, `Name`, `Position`, and at least one known
attribute header. It preserves exact numbers, ranges, and visibly absent cells,
normalizes common displayed positions, and rejects duplicate identities or
malformed rows instead of silently producing an incomplete player universe.
The caller can now provide the result count displayed by FM; the merged unique
UID count must match exactly or import fails. Recruitment requires this count.

This is not yet approved as the definitive external-player universe. Multi-file
merging, overlap deduplication, and count mismatch behavior are covered by
automated tests. A real Player Search export must still establish stable
identity, exact/ranged/unknown syntax, and agreement between its displayed
result count and parsed unique-player count.

The owned-squad importer now handles that evidence directly. It merges partial
stock views by unique normalized name, rejects duplicate names or conflicting

Position falls back to the live manager-visible squad position when a category
view omits it. This exception is limited to the controlled owned squad; it is
not permission to use name-only identity for the much larger external-player
universe.

The Physical export passed a 17-player completeness check with 136 exact
observations and exercised the complete recommendation pipeline. Only 8 of the
role catalogue's 32 inputs were present, so the resulting football scores were
classified as provisional. Mental, Technical, and Goalkeeping views remain
necessary for a decision-quality owned-squad result.

## Visible-attribute render-path tracing

The next preferred research path works backwards from a raw attribute byte
toward the code that renders the manager-visible exact value, range, or unknown
marker. This is distinct from finding and decoding the complete manager-
knowledge object graph: it asks FM for the already-resolved display answer.

The current preferred outcome is a screen-independent query of FM's own
visibility logic, after a separate discoverability check. A faithful
reimplementation is Plan B if the native path cannot be made safe and
repeatable. Passive rendering traces are verification evidence, never a
production dependency. Calling an internal function cannot enter the
production adapter merely because one replay appears to work: its object
contract, threading, side effects, and failure modes must be established.

Pinned source establishes the first address path. The player attribute block
starts at `player + 0x164`; Passing is at block offset `0x16`, making its raw
byte address `player + 0x17a`. A new research-only resolver locates a player by
stable ID in the live person collection and emits this transient address
without reading or logging its value. It successfully resolved an owned-player
Acceleration target in the supported live build on 12 September 2026.
It can also resolve FM's current active object when a player profile is open,
so external trace cases do not require a UID from an HTML export.

Available dynamic tools are GDB, `perf`, `strace`, and `ltrace`. Host
`kernel.perf_event_paranoid=4` prevents unprivileged non-stopping `perf`
watchpoint sampling. GDB supports hardware watchpoints and Intel processor
tracing, but attaching stops the process briefly and a raw-byte read watchpoint
may fire frequently. Dynamic attachment therefore requires a controlled target,
a bounded capture, automatic detach/continue behavior, and explicit acceptance
of the live-process risk.

The first bounded live trace reached the raw getter while FM rendered a ranged
external-player attribute. Static disassembly then established two distinct
stages in the supported executable build:

1. A virtual getter converts the stored signed byte to the 1--20 scale using
   `truncate((raw + 2) * 0.2)`, clamped to 1--20.
2. A downstream visibility function classifies the manager's knowledge and
   constructs a three-byte result used by the formatter. Its observed control
   flow has separate exact, ranged, and no-visible-value outcomes. The ranged
   branch derives lower and upper bounds around the normalized value; the
   no-visible-value branch passes sentinel markers to the formatter.

This proves the raw getter is below the visibility boundary and is therefore
not a lawful extraction point. It also shows that a completely hidden
attribute can still be read internally before the formatter suppresses it, so
"the raw byte was accessed" is not evidence that the manager can see it. The
promising passive-hook boundary is the visibility result immediately before
formatting. The next live differential will classify a ranged and a completely
unknown attribute on the same external player, recording only the visibility
state and never the hidden underlying value.

A subsequent bounded watchpoint on the external player's Acceleration byte was
triggered by redrawing the club squad's Physical table, and produced the same
raw getter and caller addresses as the profile-page trace. Static inspection of
that caller shows that, at the pre-format boundary, the player object,
attribute identifier, and three-byte visibility result are all still in scope.
This is the first evidence that one passive hook could capture multiple visible
players from a rendered squad/search table rather than requiring one profile
visit per player. The safe capture contract is deliberately narrower than the
in-memory structure: read the first two bytes as visible bounds/sentinels and
never read or retain the third byte, which can contain concealed truth even for
an unknown attribute.

`tools/fm20_visibility_capture.py` packages that experiment as a bounded
research harness. It detects the current FM PID, validates the supported
executable, calculates module-relative breakpoints, attaches GDB, and requests
detachment after a configured duration. The embedded GDB breakpoint reads the
display-attribute ID and exactly two bytes from the pre-format result. It cannot
read the third byte. The Python boundary validates and decodes those bytes,
rejects unexpected fields, and deduplicates repeated observations while
rejecting conflicts within a capture.

Every result is marked `complete: false` with `coverage: render-events-only`:
absence from a capture can mean an FM cell remained cached, not that the player
or attribute is undiscoverable. Early player-filtered and unfiltered
Acceleration-only runs recorded no events from a repeatedly opened Bath table,
matching the observed intermittent redraw behavior.

A fresh-table diagnostic subsequently recorded all eight contiguous Physical
column identifiers, `0x27` through `0x2e`. Static inspection of FM's virtual
getter found the dispatcher at RVA `0x4282970`, which maps those UI identifiers
to the non-contiguous raw attribute enum. Its inverse establishes the Physical
mapping as Acceleration, Agility, Balance, Pace, Stamina, Strength, Jumping
Reach, and Natural Fitness. This proves the pre-format hook is active on squad
tables while invalidating the original assumption that every UI identifier is
simply its raw-block offset minus eight.

After mirroring FM's runtime interface adjustment, the next narrowed live run
resolved all 392 eligible render events to stable player UIDs. The sample
contained 205 unique player/attribute observations over 31 players: 68 ranges
and 137 unknowns. GDB detached normally, and a host-visible liveness check
confirmed FM remained responsive on the same PID.

The earlier diagnostic run exposed an identity error: the render argument is a C++ interface
subobject rather than the framework's player-base pointer. FM's caller converts
it to the embedded `Person` by reading a signed runtime adjustment from its
secondary table. The harness now mirrors that conversion and validates the
result against the supported player type before reading `Person.UID`; the
earlier speculative wrapper scan has been removed. The 392-event run above
confirmed that correction on every eligible event.

The manager-knowledge trace has established a second identity relationship.
The lookup key is `Person.RowID` at `Person + 0x8`, not the stable UID. In one
bounded run, all 86 distinct lookup keys mapped directly to valid player
objects and their stable UIDs at `Person + 0xc`. Every explicit record lookup
returned null and the context-local vector was empty. Static inspection explains
why this is not the final knowledge answer: FM next calls a separate baseline-
knowledge function, takes the higher of the explicit-record and baseline
values, and writes that final byte to the caller's output. The explicit report
collection is therefore only one input to visibility; the baseline function is
the next algorithm boundary to characterize.

A fresh-table run reached that boundary for 83 distinct players. Explicit
record knowledge was zero in every event; baseline knowledge produced the
discrete levels 0, 2, 5, 7, 12, and 22. The same run captured 29 visible
Acceleration observations from the displayed squad: 15 ranges and 14 unknowns.
Players at baseline 12 appeared in both groups, proving the initial
explicit/baseline maximum is not sufficient to predict visibility.

Further static inspection found a later optional staff/report augmentation and
the actual final comparison. FM classifies the effective knowledge byte against
separate range and exact thresholds: at or above exact returns exact, at or
above range returns ranged, and below range returns unknown. The harness now
uses a thread-aware three-point trace at RVAs `0x15a51b5`, `0x15a51dc`, and
`0x15a52b5` to record explicit, baseline, initially merged, and final effective
knowledge together with both thresholds and the resulting classification. It
does not read an attribute value.

The first final-comparison capture produced 287 distinct decisions for 79
players: 173 unknown, 109 ranged, and 5 exact. Explicit knowledge was zero in
all 287 decisions; final effective knowledge equalled the baseline/initial
merge in this sample, so the optional staff/report object did not raise any of
them. This validates the comparison rule and shows that thresholds vary by
rendered field: a single player's effective knowledge can legitimately clear
one field's range threshold but miss another's.

That first event contract did not preserve the display-attribute selector, so
it could not pair each decision with the corresponding visible cell. Static
inspection of the enclosing function shows that the selector arrives in `r8b`
at RVA `0x15a4dc0` and remains separate from both the thresholds and attribute
value. The harness now captures that selector at function entry, carries it
through the thread-local decision record, and maps supported IDs through the
same verified display map as visible-result events.

A fresh-table retry validated the association live. It recorded all eight
Physical decisions for each of 26 players (208 cells total), plus 26 visible
Acceleration results. Every visible result had exactly one corresponding
Acceleration decision and all 26 classifications matched: 14 ranged and 12
unknown. Across all 208 Physical decisions, the exact threshold was consistently
38 points above the range threshold. The harness now enforces the visible/result
classification match as a fail-closed invariant whenever decision tracing is
enabled.

Static inspection of the renderer also identifies the cache-independent
boundary for the next experiment. At RVA `0x1d97a35`, FM calls the visible-result
builder at RVA `0x15a4a90` with the manager/UI context, a three-byte result
destination, the player's render interface, the display-attribute ID, an
optional report object, and a small caller-owned context object. Only after that
call does FM format the first two bytes for display. Reusing the table's final
string cache would couple extraction to UI lifetime and scrolling; a controlled
replay or faithful reimplementation of this builder for an independently
verified discoverable-player set is therefore the preferred next boundary.
Two guarded same-cell replays reproduced an already-rendered Acceleration cell
on its original UI thread and matched FM's two public result bytes exactly. The
first run detached normally and FM remained responsive. A subsequent experiment
then tried to chain a different attribute from the replay return boundary. Only
the original Acceleration result completed, after which FM crashed and its PID
disappeared. Chained or different-attribute invocation is therefore unsafe and
has been removed from the harness. The retained same-cell replay is research
evidence only and is not an application data source.

Static inspection nevertheless exposes the range construction without another
call into FM: classification `0`, `1`, and `2` maps to unknown, ranged, and
exact output respectively; ranged bounds are deterministic functions of the
raw 1--20 value, player/attribute seed, report quality, and player context. The
research-only reimplementation below was an interim investigative route. The
preferred production route is now to ask FM itself in a cold query, if safe.
Either route must fail closed for any input whose mapping has not been proven.

The first read-only validation used the restarted copy of the same save and
stable player IDs from the earlier external-team capture. The implementation
reproduced all 17 ranged Acceleration cells exactly, including every one of the
seven seed branches, without attaching a debugger or invoking game code. The
implementation is not connected to production queries yet.

Static inspection has now recovered the four complete threshold lookup
profiles used for goalkeepers, defenders, midfielders, and attackers. For all
supported entries, the exact threshold is the range threshold plus 38. The
eight Physical entries reproduced all 208 thresholds from the earlier
26-player passive capture. Unsupported position-family/attribute combinations
follow a zero/default branch in the executable; the reimplementation treats
those as unresolved and fails closed rather than interpreting zero as public
knowledge.

The profile-selection wrapper is also understood. It tests the 15 raw position
ratings in this order: Goalkeeper at least 18; Striker or any Attacking
Midfielder rating at least 18; any Defender rating at least 18; otherwise the
midfielder profile. This threshold is distinct from the lower threshold used
to produce the bridge's public position labels. A read-only snapshot of the
same 26 players' position bytes selected exactly the profile required by all
208 captured Physical decisions: 3 goalkeepers, 9 defenders, 6 midfielders,
and 8 attackers. No debugger was attached and no game function was called.

The final merge is now statically recovered as well: effective knowledge is the
maximum of the explicit record value, the baseline relationship value, and an
optional report value at the verified report-object field. The pure
implementation covers and validates this merge. Sourcing the baseline value
without invoking FM remains the classification gate. The ranged-bound path
also needs the verified report-quality fields, while a verified discoverable-
player collection remains the collection-level production gate.

A read-only identity join also rules out a tempting shortcut: 81 prior
baseline events all belonged to players contracted to the same club (apart
from two players currently loaned in), yet their values spanned 0, 2, 5, 7,
and 12. Baseline knowledge is therefore player-sensitive and cannot safely be
assigned once per selected team. Static inspection shows player reputation and
several manager/player relationship checks on the path before a final knowledge
helper; that helper is the next reimplementation target.

### Baseline helper, next screen-independent query step

Offline disassembly of the same supported executable (SHA-256
`fd2c877ef28927dc63b0009ec6a2d46bdba158f456a29ecb342062cb9d82b102`)
locates the baseline function at RVA `0x15a53f0`, called at `0x15a51d7`, and
its final adjustment helper at RVA `0x15a6210`. This inspection read only the
executable on disk; it did not attach to FM or read the current save.

The baseline function has distinct relationship paths, not a single team
lookup. Depending on manager/player affiliation and other checks, it passes
base levels of 0, 15, 20, 30, 50, or 80 into the adjustment helper; separate
early exits return 100. One path derives a base from reputation rather than a
fixed level. The adjustment helper normalizes a field on an object obtained
from the manager-side context and checks another relationship/context object
before returning a clamped result. These are control-flow findings, **not yet
a complete field mapping**: the virtual calls, the field meaning, and the
related-object identity must be resolved and compared with passive decisions
before production may calculate baseline knowledge.

Further offline disassembly narrows the helper at RVA `0x15a6210`. Its second
argument is the object returned by the caller's virtual method at slot
`0x748`; this object has two signed rating bytes at `+0x2c` and `+0x2d`.
A virtual selector on the first argument (slot `0x190`) chooses `+0x2c` when
its result is at least 23, otherwise `+0x2d`. The selected byte uses the
same signed-byte-to-1--20 normalization as other FM ratings. **Neither the
selector's meaning nor the two rating fields is proven yet**; calling the
selector "age" or either byte "scouting knowledge" would be speculation.

The arithmetic *after* selection is now isolated in the research-only
`tools/fm20_baseline_model.py`. Starting from the caller's relationship base,
the helper adds `4 × (rating − 10)` for ratings 1--3 and
`2 × (rating − 10)` for ratings 4--20, clamps below zero, then may add 20
after a separate relationship predicate and clamps to 100. The predicate
follows a virtual call at slot `0x420` and a context comparison through
`+0x140`; its identity and semantics remain unresolved. Synthetic inputs
show this arithmetic can produce the previously observed levels 0, 2, 5,
7, 12, and 22, but that **does not** validate which branch or fields produced
any particular player's result.

The next bounded live calibration needs to record, for each baseline decision,
only the relationship-base branch, chosen normalized rating, bonus predicate,
and final baseline level, keyed by player UID. These are knowledge inputs,
not underlying player attributes. It must verify object identity and compare
the pure model with passive FM results before the mapping enters production.
The existing render hook can supply calibration events, but production must
later query the same mapped inputs directly from read-only process memory with
no open table or profile. A truly cold, unopened-player comparison is the
acceptance test; render-cache coverage is not.

### First live helper calibration — 13 September 2026

With the same 20.4.4 executable running and the save at 24 June 2019, a new
bounded passive trace sampled the helper at its selector, normalized-rating,
optional-bonus, and return boundaries. It performed no replay or game-function
call. An idle-screen 15-second capture produced no events, as expected for
cached rendering. Opening external Squad → Physical tables for calibration
then generated events; GDB detached normally and FM remained running.

The second table produced 122 distinct baseline-helper events and 60 public
Acceleration observations. Every helper output matched the independent pure
arithmetic model or the capture would have failed closed. All 122 used one
observer object, normalized rating 3, and no bonus in this sample. A separate
read-only memory join placed that observer object at `active human-manager
base − 0x28`; both selected rating bytes currently normalize to 3. This
identifies the rating *owner* as the active manager, but not yet the semantic
names of the two fields or the selector.

The caller return address separates starting-level paths. Of the 122 events,
115 came from the dynamic branch returning at RVA `0x15a58d4`, four from the
zero/20 relationship branch at `0x15a5945`, two from the branch at
`0x15a5789`, and one from the fixed-50 branch at `0x15a5606`. Dynamic
starting levels included 25, 30, 33, 35, and 40. Static inspection of this
branch shows a manager/player relationship score being combined with a
player-side virtual 16-bit scale getter in four bands (`<3000`, `3000--3999`,
`4000--4999`, and `≥5000`) using coefficients 0.05, 0.10, 0.15, and 0.20.
The getter is plausibly reputation but is not semantically verified; the pure
model calls it a player scale. At score 100, the branch produces starting
levels 25, 30, 35, and 40 respectively. The score's source includes a
manager-owned cache and a fallback calculation; neither has been fully mapped
or verified for unopened players. A third bounded trace was instrumented to
capture only this score and pointer identities, never the underlying scale
value, but saw no fresh render events. The next successful trace must capture
that *knowledge score* and test whether a cold read of the manager-owned
structure yields the same input.

If native invocation proves unsafe, the Plan B implementation checkpoint is a
read-only input snapshot for this helper, with each field named and validated,
followed by a fresh matched capture of inputs and FM outputs. The earlier 81
per-player baseline results do not contain enough input detail to validate the
model on their own. Either production route must match FM's visible results for
players whose profiles and tables have not been opened in the session. No
renderer cache or debugger replay is an admissible production dependency.

### Plan A: FM-owned, screen-independent visibility query

Offline call-site inspection on the pinned executable found that the visible
result builder at RVA `0x15a4a90` and its classification core at RVA
`0x15a4dc0` have callers outside the already-traced table formatter. In
particular, RVA `0x22dc630` resolves a manager interface to a knowledge
context through the global context vector; RVA `0x22dc790` wraps the
three-byte builder; and RVA `0x50a0450` wraps the classification core. The
classification wrapper has numerous call sites beyond the one table-rendering
path. This is evidence that the visibility calculation is factored out of
rendering, **not** yet proof that an arbitrary unopened player can be queried.

A read-only inspection of the running 20.4.4 process on 13 September found a
well-formed global vector with one knowledge context. Its owner pointer was a
human-manager `Person` object, and its ID matched the active employed manager.
No game code was invoked, no attribute values were read, and no screen was
opened for this check. Because this process had displayed external tables
earlier, context presence alone is not proof that a fresh session initializes
it before any player screen is visited.

Two fail-open hazards make the wrappers unsuitable as a public API without
additional guards. The builder wrapper at RVA `0x22dc790` seeds all three
output bytes with the *underlying exact attribute* before trying to resolve a
manager context; if that lookup fails, it returns those raw bytes unchanged.
The classification wrapper at RVA `0x50a0450` likewise returns class `2`
(exact) on several missing-context paths. A bridge must verify the active
manager, valid context index, non-null context, and owner identity **before**
calling the builder; it must never publish the third result byte, which can
hold concealed truth even when the first two bytes mean unknown.

The core path is not demonstrably read-only. Its explicit-knowledge lookup at
RVA `0x15a5d80` updates two recent-lookup fields in the context, and the core
may lazily resolve and store a report pointer. Other virtual callees still
need a side-effect audit. Normal FM callers may make these writes harmless,
but an out-of-thread debugger or bridge call has not been proven safe; the
earlier different-attribute replay crash remains a concrete warning.

The first Plan A checkpoint was a strict, read-only preflight of arbitrary
player identity and active-manager context, followed by an exploratory native
call in the disposable save. The builder's player argument is an adjusted C++
interface, not the `Person` pointer. A one-time passive pointer capture found
the adjustment to `Person` was `+0x1c0`, which gives a player interface at
`Person − 0x1c8`. A read-only scan validated that inverse for 500 of 500
loaded players, not merely players in the displayed club. The active manager
interface was independently located at `HumanManager Person − 0x480`.

The first GDB register-injection attempt stopped in padding immediately before
the builder. The live builder byte matched the executable, and FM remained
responsive; the GDB method was abandoned without treating the stop as an FM
visibility result. A direct Linux `ptrace` harness then set the Windows x64
call frame on FM's primary thread, disabled restart of the interrupted syscall,
called the builder at RVA `0x15a4a90`, trapped at its return, read only the
first two public bytes, restored registers, and detached. Four external-player
calls completed: two ranged Acceleration results and one unknown Acceleration
result exactly matched their earlier passive UI captures; a different Passing

### Preflight hardening and same-session reproduction — 13 September 2026

`preflight()` (shared by both cold-call tools; `fm20_cold_visibility_ptrace.py`
imports it from `fm20_cold_visibility_call.py` rather than duplicating it) had
no test coverage. Its memory-graph resolution — context-root traversal, the
human-manager/player interface adjustment arithmetic, and player-uniqueness
matching — is now factored out as `resolve_cold_call_addresses`, a pure
function of an already-open memory descriptor, module base, player ID, and
the already-verified active manager's ID. Ten new tests in
`tests/test_fm20_cold_visibility_call.py` build a synthetic memory graph with
a tempfile-backed fake `/proc/<pid>/mem` and assert each guard fails closed:
missing context root, more than one context, a null context, a non-human-
manager owner, an owner that is not the active manager, a wrong manager or
player interface adjustment, and zero or multiple player matches. This
refactor changes no runtime behaviour; the full suite (200 tests) still
passes. Both tools also gained `--dry-run`, which runs preflight only and
never attaches, for safer verification before any live call.

Separately, the `fm20_cold_visibility_ptrace.py` timeout path is hardened: if
the builder does not reach its return trap in time, the harness forces a
`SIGSTOP`, restores the pre-call registers, and detaches as before, but now
raises a distinct error afterward instead of silently resuming FM. The
builder can lazily write lookup/report state, so abandoning a call mid-flight
is not provably harmless; the caller is now told explicitly to verify FM's
health before attempting another cold call.

With FM running and an unopened Lincoln City still the target, fresh
`--acknowledge-native-call` invocations of the (refactored, retested) ptrace
tool reproduced both previously recorded cells exactly: Michael Bostwick's
Acceleration as `5–10` and Passing as `10–15`. FM's process state was checked
between and after both calls and remained healthy (running, not stopped or
zombied). This confirms the cold-call path survived the preflight refactor
and is reproducible across independent invocations in the same session; it
does not yet satisfy the fresh-FM-session or in-UI verification legs of the
acceptance test, and the optional report-object parameter is still hardcoded
to null with no known offset, collection, or lookup key anywhere in the
codebase — determining when FM needs one remains unexplored and requires new
disassembly, not a harness change.

Three further fresh, non-chained calls extended coverage beyond Bostwick and
beyond the Physical category: Josh Vickers (goalkeeper, Lincoln City) returned
a `handling` range of `11–16`; Jorge Grant (midfielder) returned an `unknown`

### False-positive root cause found and fixed — 13 September 2026

The user checked real UI cells against cold-call output and found two false
positives: Charlie Sheringham's Finishing showed `3–9` cold but `-` in FM's
own exported attribute page, and Daniel Grimshaw's Reflexes showed `8–13`
cold but `-` in his. A systematic check ruled out an attribute-ID mapping
error as the cause: `heading` and `passing` returned Bostwick's exact correct
ranges but fabricated ranges for Sheringham on the same IDs, which is only
possible if the IDs themselves are right and something else is wrong. A full
32-attribute sweep against Sheringham's own exported page (every attribute
`-`) found 8 false-positive ranges; a 33-attribute sweep against Grimshaw's
page found 3 (`aerialReach`, `reflexes`, `rushingOut`), while his 4 real
Goalkeeping ranges (Command of Area, Handling, Kicking, Throwing) all matched
exactly.

The cause was found by building `tools/fm20_builder_call_arguments.py`, a
passive hook at the same builder entry address the cold-call tools target,
recording FM's own arguments for a genuine, screen-triggered call without
ever calling into FM. Two restarts were needed to get a true fresh (non-
cached) render: an in-place tab switch produced no events (as expected for a
cached cell), and a first post-restart attempt was armed before the user had
navigated back to the page. A capture during a genuine fresh navigation to
Sheringham's profile recorded 77 real builder calls. Every one had
`reportObject = 0x0`, confirming that argument was already fabricated
correctly. Every one also had `smallContext` bytes with offset 0-7 equal to
zero and offset 8 equal to `0x01`, followed by a real, call-varying 7-byte
value at offset 9-15. Both cold-call tools had fabricated offset 0-7 as the
*manager interface pointer* (a large, constant, nonzero address) and offset
8-15 as the plain 8-byte integer `1` (zero-padding bytes 9-15) -- offset 0-7
was simply wrong, a real bug, not a semantic guess that happened to differ.

Setting `smallContext`'s first 8 bytes to `0` instead of the manager pointer
(both `tools/fm20_cold_visibility_ptrace.py` and `tools/fm20_cold_visibility_call.gdb`;
the manager-interface value itself is no longer written into the call at all)
eliminated every false positive: the same 32-attribute Sheringham sweep, the
33-attribute Grimshaw sweep, and the original 32-attribute Bostwick sweep
each returned 0 mismatches out of 97 attribute checks total, with no
regressions. FM remained healthy throughout. The call-varying 7-byte value at
`smallContext` offset 9-15 is still unexplained and still fabricated as zero;
that it produced zero mismatches across 97 checks is evidence it is not
load-bearing for the exact/range/unknown decision on these three players, but
it has not been proven irrelevant in general and remains an open question,
same as the still-unexplored `reportObject` non-null case.

### Formalized query entry point — 13 September 2026

Further live spot-checks after the fix (Bobby Grant, Curtis Weston, an owned
Hungerford Town player with guaranteed-exact attributes, Mohamed Salah's mix
of exact/ranged Technical/Mental/Physical values, and a fresh Handling
re-check on Grimshaw) all matched expectation with FM remaining healthy
throughout, further corroborating the fix.

`tools/fm20_player_visibility_query.py` formalizes the ad hoc validation

resolve a player's stable ID by exact name (scanning loaded players'
identity fields only, never an attribute) or accept an ID directly, then
sweep any or all supported attributes through a fresh, non-chained cold call

manager see for this already-identified player," not "which players exist to
consider" -- the latter remains gated behind the unbuilt discoverability work
below.

Known gap: `punching`, `eccentricity`, `freeKickTaking`, `penaltyTaking`, and

-- discovered when Grimshaw's own exported page showed Punching `1-8` with no
tool able to query it. This is an honest gap (never reverse-engineered), not
a wrong guess; closing it needs the same offset-plus-display-ID-plus-real-export
validation already applied to every other attribute, not a plausible-looking
addition to the table.

### Discoverability investigation, first results — 13 September 2026

**Capture sequencing lesson.** Several early Player Search captures returned
zero hook hits, which was briefly misread as evidence that search results use
a different render path. They don't. The real cause was procedural: a
foreground capture's "armed" notice reaches the user only after the capture
finishes, so every fresh render happened before or after the listening
window. Captures that need a user action now run in the background, the
operator waits for the armed line, and only then asks the user to navigate.
Plain column sorts or re-entering an already-rendered screen can also hit
FM's cell cache; a full FM restart followed by first navigation was reliable.

**The render hook fires on Player Search.** After a restart, a correctly
sequenced capture during a "transfer listed" Player Search recorded 3,864
hook hits on display IDs `0x19`--`0x26`, the Mental block (that search view
was showing Mental columns). One of those IDs, `0x20`, is absent from
`DISPLAY_ATTRIBUTE_IDS`; it sits between Flair (`0x1F`) and Off The Ball
(`0x21`), where Leadership falls alphabetically. That is a lead for one of the
known missing attributes, not a verified mapping.

**Search membership matched a real export exactly.** A second capture with
identity resolution enabled for all attributes recorded 32 visible-result
events (4 visible Mental columns × 8 rows), all 32 resolved to player
identities through the known `+0x1c0` interface adjustment. The 8 distinct
player IDs mapped to exactly the 8 names in FM's own export of the same
filtered search (`SearchListed.html`, exported earlier on the same unadvanced
save date), and FM itself reported "8 players found": no extras, none
missing.

**What this proves and what it doesn't.** It proves the existing render hook
observes exactly the rows a Player Search draws, which makes it a strong
comparator for validating any future discoverability source against real
searches. It is not itself a discoverability source: it only sees rows that
are actually rendered, so it depends on an open screen, scrolling, and FM's
cache, the same limitation already recorded for passive capture elsewhere in
this document. The next step is to locate the in-memory collection holding a
search's result set while the screen is open (by scanning process memory,
read-only, for a pointer array containing exactly these players), then trace
what code builds it.

### Discoverability investigation, memory-structure findings — 13 September 2026

All checks below were read-only scans of process memory while a Player Search
screen was open; no FM code was called.

**A persistent listed-players block is not the live result list.** A block of
47 fixed-size (0x48-byte) records at a heap address held, per record, a player
pointer (several copies), the active human manager's pointer (ID verified),
and the player's club. It contained 7 of the 8 transfer-listed search results
and 39 of the 50 loan-listed results, and none of 262 exported free agents or
the 17 owned first-team players. After the user changed the filter from
transfer listed to loan listed, the block was byte-for-byte identical, so it
is not the search's live output. It may be a store of listed players that a
search reads from, but that interpretation is unverified.

**No compact ID arrays.** A scan for tight arrays of the players' 4-byte UID
or `Person.RowID` values found none; FM does not hold these result sets as
ID lists.

**Unsorted search output follows global person-collection order.** The global
person collection held 259,080 entries (162,072 players) in this process. The
40 uniquely-named players in the loan-listed export appeared in strictly
increasing collection-index order (0 inversions). The transfer-listed export
did not, but that view was visibly sorted by Value, and the free-agent export
formed ascending runs consistent with a sort on another column. This fits a
search that filters players in collection order before any view sort, but is
not direct proof of the search code.

**A large ordered player array was a container, not a pool.** A page-level
scan briefly suggested a 50-player block; walking it showed a 790-player
array in strict global order, covering a narrow global-index range, containing
3 owned squad players and 5 loan-listed players but no transfer-listed, free
agent, or known unscouted players, and bounded by non-player entries. It is
another person container derived from global order (likely including staff),
not a discoverable-player universe. No pointers to its apparent bounds were
found.

**Change of approach.** Memory scans for the result list keep surfacing
ambiguous copies. The next step traces behaviour instead: passive breakpoints
on the already-known manager-knowledge functions record their callers' return
addresses while the user changes a search filter, to locate the search's
filtering code and establish whether a manager-knowledge check is part of the
search predicate.

### Discoverability investigation, static knowledge call-site map — 13 September 2026

**Live caller tracing so far.** `tools/fm20_search_caller_trace.py` places
passive breakpoints on seven known knowledge functions and counts their
callers' return addresses. An idle smoke test attached, set all breakpoints
without error, kept all FM threads running, and detached cleanly. Three armed
windows (3, 4, and 10 minutes) recorded no callers at all; no search or redraw
is known to have happened during them, so these are not evidence either way.
Future windows are armed only after the user confirms they are at the screen.

**Static call sites.** A read-only scan of `fm.exe` on disk for direct
`call`/`jmp` targets found: visible-result builder 4 call sites (including the
known table formatter at RVA `0x1d97a35`, which validates the method),
classification core 9, baseline knowledge 5, explicit-knowledge lookup 2,
knowledge-context resolver 20, builder wrapper 1, and classification wrapper
22. Grouping by the executable's exception-directory function table
(239,363 functions) shows one 64KB function at RVA `0x1d859b0`--`0x1d9552b`
containing 10 of these call sites across four of the functions, consistent
with a large per-column or per-field switch.

**Three small knowledge primitives** (disassembled with `objdump`; names are
descriptive, not symbols):

- `0x1fb1860` returns a player's effective knowledge level. It resolves the
  manager's knowledge context from the same global root used by the cold-call
  preflight (RVA `0x746A440`); if that fails it returns 100 (full knowledge,
  fail-open). Otherwise it returns the maximum of the explicit knowledge
  record's byte and the baseline knowledge function's result, with no report
  object. This is plausibly FM's "knowledge %" for a player and a candidate
  input to any "players I know about" search filter, but its callers are not
  yet identified.
- `0x1fb1910` resolves the context and calls the classification core with
  selector `0x50`, outside the attribute display-ID range, mapping unknown to
  `0x12`, ranged to `0x10`, and exact to a caller-supplied default. It likely
  governs visibility of a non-attribute field; which field is unverified.
- `0x1fb19e0` returns exact (class 2) immediately when three global flags are
  all set, one of them in FM's main game structure; otherwise it classifies a
  caller-supplied selector through the core, and also returns exact when the
  player or context is missing. The flags plausibly implement FM's "attribute
  masking" game option, but that is unverified.

These are building blocks, not the search loop.

**Callers of the primitives.** The knowledge-level function `0x1fb1860` has 18
direct call sites across many unrelated functions, including one in the 64KB
function and three tiny, near-identical wrappers (about 0xc9--0xcd bytes each)
at `0x3d951d5`, `0x3d992d1`, and `0x3d9f7a1`; repeated per-type wrappers of
this shape are typical of generated binding or filter-evaluator code, which
makes them priority candidates. The field-visibility function `0x1fb1910` has
5 call sites, three of them in one function at `0x547c390`. All 8 call sites
of the masking-override classifier `0x1fb19e0` are inside a single 34KB
function at `0x5231a30`, which also contains 2 classification-wrapper calls.
None of the three primitives is referenced as a stored 8-byte function
pointer.

**Field checks in the 64KB function.** Its three resolver/classification-core
pairs each classify a non-attribute selector (`0x53`, `0x53`, `0x52`) for a
player object held in the function's frame, and continue only when the result
is exact (class 2). They gate some fields on full knowledge, as `0x50` does
in the field-visibility primitive; which fields these selectors name is
unverified.

**The "wrappers" are function chunks, and three candidates are virtual
methods.** The three small blocks at `0x3d951d5`, `0x3d992d1`, and
`0x3d9f7a1` have no direct calls, no `lea`-loaded addresses, and no stored
pointers: they are separately-listed chunks of larger functions, not
standalone callables. Each obtains a knowledge level from `0x1fb1860`, then
walks a pointer list on the player object (begin/end at `+0x1e0`/`+0x1e8`),
lazily resolving each entry's handle and matching it against a person ID;
if a matching entry passes a virtual check (vtable slot `0x700`) the chunk
takes a different return path, otherwise it returns the knowledge level. So
knowledge level is overridden by some per-player relationship record; what
that relationship is remains unverified. The 64KB function `0x1d859b0` and
`0x547c390` have no direct callers but each appears in a table of 16
contiguous code pointers (a vtable), so they are virtual methods; the 34KB
function `0x5231a30` has two direct callers and also appears in such a table.

**Class names from RTTI.** The executable carries MSVC run-time type
information, so each vtable's complete-object locator names its class:

| Function | Class | Slot | Hierarchy |
| --- | --- | --- | --- |
| `0x1d859b0` (64KB) | `GAME_PLAYER` | 6 | `db::EXTERN_PLAYER`, `PERSISTENT_PROPERTIED`, `PROPERTIED`, `PERSISTENT` |
| `0x5231a30` (34KB) | `db::PLAYER` (this-offset 16) | 2 | `db::PERSON`, `db::DATABASE_RECORD`, `PROPERTIED` |
| `0x547c390` | `PERSON_POSITION_FILTER_RULE` | 27 | `PERSON_FILTER_RULE`, `sitoolkit::FILTER_COMPARE_RULE<db::DATABASE_RECORD_FILTERABLE>`, `sitoolkit::FILTER_COMPARE_RULE_BASE`, `sitoolkit::FILTER_RULE_BASE`, `sicore::DERIVABLE_RECORD`, `sicore::RECORD` |

This is the most significant discoverability lead so far. FM's search
filters are objects in a `FILTER_RULE` class family, evaluated against
database records that implement `DATABASE_RECORD_FILTERABLE`, and the
position filter rule consults the knowledge-gated field-visibility function,
so at least that criterion respects manager knowledge rather than raw
database truth. Both large knowledge-checking functions are methods of the
"propertied" player classes, consistent with property getters whose values
are masked by manager knowledge. Slot meanings are inferred from position
and callees, not symbols.

**Class inventory.** A scan of RTTI type names for filter, search,
scouting, knowledge, interest, and shortlist terms found, among many UI
panel classes:

- a search executor pair, `GAME_PERSON_SEARCH` and `db::EXTERN_PERSON_SEARCH`,
  plus `CLIENT_SEARCH`;
- a scouted-person store, `GAME_SCOUTED_PERSON` / `db::EXTERN_SCOUTED_PERSON`
  (with `_TAG` variants), and singletons `SCOUT_MANAGER` and `SHORTLIST_MAN`;
- a filter framework in `sitoolkit` (`FILTER`, `FILTER_LIST`,
  `FILTER_CONTEXT`, `FILTER_RULE<T>`, `FILTER_COMPARE_RULE_BASE`,
  `FILTER_RULE_BASE`, `FILTERABLE`) with record type
  `db::DATABASE_RECORD_FILTERABLE`;
- about 105 concrete filter-rule classes, including ones directly relevant to
  discoverability: `PLAYER_SCOUTED_FILTER_RULE`,
  `PERSON_CAN_BE_SCOUTED_FILTER_RULE`, `HIDE_PLAYER_FILTER_RULE`,
  `PERSON_INCLUDE_OWN_FILTER_RULE`, `DATABASE_SIZE_FILTER_RULE`,
  `PERSON_TRANSFER_LISTED_FILTER_RULE`, `TRANSFER_STATUS_FILTER_RULE`, and the
  `PERSON_INTERESTED_*_FILTER_RULE` family;
- `MANAGER_ASK_EXPAND_SCOUTING_RANGE_RULE`, confirming FM models an explicit
  manager scouting range.

For rules sharing the person-filter-rule layout, vtable slot 27 is a
candidate evaluator (the position rule's slot 27 is the function that
consults field visibility); vtable sizes vary widely, so slot 27 is not
assumed for other layouts. The central discoverability question is now
concrete: does a search evaluate its rules against all loaded players, or
against a pool that is already restricted (for example by scouting range)?
The caller trace now also counts distinct second arguments per evaluator,
which approximates the number of records a search tests.

**Evaluator contract and search-executor methods.** Disassembly of three slot
27 evaluators (transfer listed `0x547bb70`, player scouted `0x553a2b0`,
interested loan `0x1fb1f30`) confirms the shape: `this` is the rule, the
second argument is the record under test (its `+0x8` object is read), and a
third argument carries context. The transfer-listed and player-scouted rules
fetch a tagged property through a virtual call at rule vtable `+0xe0` and
scan the rule's own tag list for `0x666c766c`; the player-scouted rule then
compares the value against 30000. The interested-loan rule first tests a
global flag adjacent to the attribute-masking flags. RTTI gives
`GAME_PERSON_SEARCH` a 13-slot primary vtable (slots 4--12 at `0x1d62750`,
`0x1d65010`, `0x1d635f0`, `0x1d63f50`, `0x1d62e50`, `0x1d63340`, `0x1d66930`,
`0x1d671d0`, `0x1d67110`); slot 8 (`0x1d62e50`) is one of the functions the
static scan found calling the manager-knowledge context resolver twice, so
the search executor itself consults manager knowledge. `GAME_SCOUTED_PERSON`
(`0x1da87d0`), `SCOUT_MANAGER` (`0x25894c0`, `0x25a5520`), `SHORTLIST_MAN`
(`0x25c4120`, `0x25e3660`), and the differently laid-out
`PERSON_CAN_BE_SCOUTED_FILTER_RULE` have also been located and added to the
live trace. `db::EXTERN_PERSON_SEARCH` and `db::EXTERN_SCOUTED_PERSON` have
no complete-object locators of their own (interface-only in this build).

**`GAME_PERSON_SEARCH` slot 8 acquires knowledge; it is not a filter test.**
It requires a person interface and a second object whose byte `+0x24` equals
3 and whose `+0x30` handle resolves. It resolves the manager-knowledge
context and calls a further knowledge-module function at `0x15a5ac0` with
that context, the person, and a level byte. It then searches a list on the
second object (begin/end at `+0xd0`/`+0xd8`) for the person's ID and, if
absent, allocates and appends a new entry stamped with FM's current game
date (the same date field the probe reads at RVA `0x7386EE0`). This reads as
recording that the manager has discovered or gained knowledge of a person.
It writes game state, so it must never be invoked from research or bridge
code; it is relevant only as evidence of how discoverability is accumulated
and as a pointer to a candidate per-manager list of discovered people.

**The explicit-knowledge writer and store.** `0x15a5ac0` takes the knowledge
context, a person, a target object, and a level byte (255 meaning "compute
it", via `0x15a5f90`, which itself calls the baseline knowledge function).
It finds the person's record in a pointer vector on the context (begin/end at
context `+0x0`/`+0x8`), keyed by the person's `RowID` at record `+0x0`, using
the one-entry cache at context `+0x20` (index) and `+0x24` (key) noted
earlier. A positive level is written as `min(level, 100)` to the record's
byte `+0x8`; a level of zero or below removes the record (`0x15a4960`); a
missing record is inserted (`0x15a5eb0`). So the manager's explicit
knowledge is a flat, directly readable vector of `{RowID, level}` records on
the same context object the cold-call preflight already verifies. Explicit
knowledge is only one input to effective knowledge (baseline and reports are
others), so this store is not by itself the discoverable universe.

**The explicit store is empty in this save.** A read-only read of the
active manager's knowledge context (ID verified) found an explicit-record
vector with 0 entries and an unused lookup cache (index and key both -1),
after two Player Searches had been run in the session. Two consequences:
every visible range observed in this save is derived from baseline
knowledge, not explicit records; and running Player Search did not create
explicit knowledge, so the acquisition path in `GAME_PERSON_SEARCH` slot 8
belongs to some other activity (plausibly scouting). This raises a simpler
hypothesis to test before further tracing: that Player Search can return any
loaded player (162,072 in this process), with attribute masking alone
controlling what the manager sees. A user-driven check of the unfiltered
result count and of name searches for known-unscouted players is the next
step.

**Registry correction.** The only memory match for the `GAME_PERSON_SEARCH`
primary vtable was not a live search: it sits in a table of 0x30-byte entries
pairing vtables (including `GAME_PLAYER` and `GAME_SCOUTED_PERSON`) with type
codes, which reads as a class registry. It held no player lists.

**Tracer readiness.** The caller trace now covers 36 functions (knowledge
primitives, 8 filter-rule evaluators, `GAME_PERSON_SEARCH` slots 4--12,
scouted-person, scout-manager, and shortlist methods) and records distinct
second arguments per function. An 8-second idle attach recorded no calls and
left FM healthy.

The first identity decoder resolved 3,966/4,320 and 4,551/4,933 IDs. All
remaining 354/382 pointers had the `db::ACTUAL_PLAYER_AND_NON_PLAYER`
primary RTTI class instead of `db::ACTUAL_PLAYER`; their person-identity
header is at candidate `+0x2a0`, whereas ordinary players use `+0x1c8`.
Read-only verification of the alternate header resolved all 382 remaining

4,320 and 4,933 respectively, with the exact 613-ID increase. The research
tracer supports both layouts. No concealed attribute bytes were used to
establish membership.

This is strong validation of the *observed* search sets, not yet a cold
discoverability source: `GAME_PLAYER` slot 6 is downstream of candidate
selection. Next trace the caller chain and accepted-result insertion path
back to FM's package-aware candidate producer, then test invoking or reading
that producer without opening Player Search. Attribute visibility remains a
separate native query.

Static RTTI on the transfer-listed rule's caller identifies function
`0x42c96a0` as slot 9 of the generic filter vtable family (including
`DB_RECORD_FILTER`, `CLUB_LIST_FILTER`, `COACH_FILTER`, and the base
`sitoolkit::FILTER`). It is a filter-list evaluator, not the package-aware
candidate producer. A further passive trace targeted its *caller* during
one search refresh to move upstream to the search executor.

That trace found one caller of the generic evaluator at `0x5276efb`, inside
function `0x52769e0`--`0x5277306`. Its disassembly iterates a pointer vector
at its first argument `+0xd0/+0xd8`, applies the filter via a virtual call,
and appends accepted entries to an output vector. The function has one direct
caller at `0x1f63307` (inside chunk `0x1f62b77`--`0x1f6336e`). The caller
performs a per-record indexed bitset test before the filter pass; this is a
candidate package gate, **not yet identified as such**. The surrounding
caller also allocates/date-stamps records and changes vectors, so it must not
be cold-invoked on the basis of this disassembly. Next capture the vector
length and bitset/context pointers at `0x52769e0` under both packages and
trace the owner of the bitset to FM's package state. The eventual cold query
must reproduce the exact 4,320/4,933 sets without any Player Search redraw.
