# 03.3 — Boundary enforcement

## Goal

Make FMBridge the point at which hidden players and hidden field values become
structurally unavailable to the rest of the system.

## Work

1. Separate framework/raw types from public DTO types by assembly or namespace.
2. Build DTOs from verified knowledge structures and explicit field allowlists.
3. Avoid APIs that accept a hidden value alongside a visibility label.
4. Validate observation invariants before serialization.
5. Redact exceptions and logs at the raw-source boundary.
6. Prevent diagnostic endpoints and serializers from reflecting raw objects.
7. Add negative tests that deliberately attempt to leak a value.
8. Build candidate collections from the verified manager-visible source and
   retain inclusion provenance.
9. Authorize single-player lookup through visible collection membership or
   another explicitly approved relationship; reject arbitrary ID probing.
10. Bound and paginate collection reads without mixing in-game snapshots.

## Exit criteria

- Python, SQLite, golden fixtures, and ordinary bridge logs never contain a raw
  hidden-value property.
- Searching serialized outputs for forbidden fields is an automated check.
- A code review can trace each public field to an approved mapping.
- Unknown values are not created by reading truth and discarding it later.
- External-player collection membership matches the controlled UI corpus and
  raw database enumeration cannot reach the public contract.
