# 03.5 — Visibility verification corpus

## Goal

Create safe, repeatable regression cases for manager knowledge.

## Corpus design

Each case records:

- scenario and knowledge relationship;
- relevant visible UI state, described without copyrighted assets if needed;
- sanitized expected bridge response;
- game/framework build and setup;
- how to recreate or recheck the case manually;
- fields intentionally omitted because their semantics are unresolved.

At minimum include owned, fully scouted, ranged, unscouted, stale-report, and
knowledge-change cases.

Collection-level cases must also include no-filter player search where
available, stable filtered searches, zero results, multiple pages, a player
entering the visible universe, and an internal player deliberately known to be
outside it.

## Recorded real-save checks

### External squad Physical table

- Build: FM20 20.4.4 Steam/Windows executable under Proton.
- Date checked: 12 September 2026, without advancing the save.
- Relationship: external top-flight club with partial manager knowledge.
- Membership: the hook resolved 31 distinct table players; the user confirmed
  the club and visible membership were correct.
- Identity: all 392 eligible render events resolved through FM's runtime
  interface adjustment to stable player UIDs; there were no unresolved or
  conflicting eligible events.
- Observations: 205 unique player/attribute results, comprising 68 ranges and
  137 unknowns. Six Physical columns were captured for every player.
- UI comparison: four representative rows were presented with sanitized player
  labels; the user confirmed every displayed range and unknown marker matched
  FM exactly.
- Mapping: FM's static dispatcher at RVA `0x4282970` establishes all eight
  Physical UI IDs without reading concealed values. Agility and Pace were not
  included in this particular dynamic sample because the old provisional map
  filtered them; subsequent captures use the corrected map.
- Intentionally absent: no third result byte, raw attribute value, CA, PA, or
  other hidden fact was read or retained.

### External-table knowledge decisions

- Build: FM20 20.4.4 Steam/Windows executable under Proton.
- Date checked: 12 September 2026, without advancing the save.
- Scope: 287 distinct final knowledge decisions across 79 players.
- Classification: 173 unknown, 109 ranged, and 5 exact.
- Inputs: explicit knowledge was zero throughout; baseline and final effective
  knowledge used the discrete levels 0, 2, 5, 7, 12, 22, and 52. No event in
  this sample was raised by the optional staff/report augmentation.
- Rule: every result matched FM's final comparison of effective knowledge
  against separate range and exact thresholds.
- Attribute pairing: a fresh-table retry captured all eight Physical decisions
  for 26 players. All 26 captured visible Acceleration observations had a
  matching decision, with 14 ranged and 12 unknown in both sources and zero
  mismatches. The exact threshold was 38 points above the range threshold for
  every one of the 208 Physical decisions.

## Exit criteria

- The corpus drives bridge-mapper and client-decoder tests.
- Names, IDs, and values are sanitized or synthetic.
- A framework/game update can be checked against the corpus without redesigning
  the test plan.
- Test data contains no hidden-value side channel.
- Collection membership, totals, pagination, and direct-lookup denial are
  regression-tested against sanitized expectations.
