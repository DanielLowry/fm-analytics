# 02.1 — Observation and identity model

## Goal

Define what a row means before defining tables.

## Required distinctions

- **Entity:** a player, club, competition, fixture, or match identity
- **Capture:** one coherent read attempt from FMBridge
- **Observation:** what was visible about an entity in that capture
- **In-game effective time:** when the fact applies in the simulated world
- **Wall-clock capture time:** when this application observed it
- **Knowledge state:** known, ranged, unknown, or unavailable
- **Discoverability:** why an external player was legitimately present in the
  manager-visible candidate universe at a capture

## Decisions to make

1. What constitutes a snapshot boundary across multiple endpoints?
2. How are saves distinguished if FM reuses entity IDs?
3. Can IDs change after save/load, database changes, or framework updates?
4. Are unchanged observations repeated or linked/deduplicated?
5. How is a disappeared entity distinguished from a failed partial read?
6. Which values are mutable facts versus slowly changing labels?
7. How is a player leaving the discoverable universe distinguished from a
   failed or incomplete collection read?

## Exit criteria

- Example timelines cover a transfer, attribute change, unknown-to-range change,
  game reload, and failed capture.
- Queries can distinguish “not observed” from “observed absent.”
- Save identity and capture consistency semantics are documented.
