# 02.2 — SQLite schema and migrations

## Goal

Implement the smallest schema that faithfully stores captures and visible
observations.

## Initial table families

- saves and source versions;
- captures and capture-resource status;
- players and clubs scoped to a save;
- squad-membership observations;
- player-field observations;
- attribute observations with visibility, exact value, minimum, and maximum;
- discoverable-player membership and inclusion provenance when Phase 03 adds
  the verified collection;
- fixtures when required by the initial importer.

Names are provisional until the observation examples in 02.1 are approved.

## Constraints

- Database checks mirror known/range/unknown invariants.
- Foreign keys are enabled.
- Migrations are forward-only and committed with the schema change.
- Raw bridge response bodies are not retained by default.
- Derived analytics values live in separate versioned tables later.
- MVP schema work is driven by current recommendation inputs; speculative match
  or market tables are deferred.

## Exit criteria

- A new database reaches head from zero.
- At least one prior migration upgrades to head without data loss once a prior
  version exists.
- Constraints reject leaked or internally inconsistent attribute values.
- Schema documentation explains temporal keys and indexes.

## Initial implementation

Schema version 1 contains `captures`, `squad_players`, `player_positions`, and
`player_attributes`. Database checks enforce percentage, boolean, club-pair,
and exact/range/unknown invariants. Foreign keys and cascading child cleanup are
enabled, although the public API does not expose deletion.

Contract/source version, in-game date, UTC capture time, manager, controlled
club, and a deterministic content fingerprint are stored on each capture.
Because no prior schema exists yet, forward migration and backup/restore gates
remain open.
