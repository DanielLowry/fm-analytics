# 00.4 — Squad extraction

## Goal

Enumerate the human-controlled club's current first team and map safe basic
fields into the bridge contract.

## Initial fields

- Stable player identifier
- Display name
- Date of birth and age as of the live game date
- Natural/accomplished playing positions needed for the printed list
- Club identifier
- Display-precision condition and match fitness
- Injury/suspension availability flags
- Contract type, dates, playing-time status where understood, transfer status,
  and contracted club (including a loan parent)

## Work

1. Define exactly what “first-team squad” means in framework terms.
2. Compare extracted membership against the FM squad screen.
3. Check loans in/out, trialists, youth players promoted to the first team, and
   players leaving on transfer.
4. Determine whether IDs survive save/reload and game advancement.
5. Map positions without interpreting suitability in C#.
6. Use an explicit field allowlist; do not serialize framework objects.
7. Probe attributes only for owned players during Phase 00. Broader visibility
   rules belong to Phase 03.

## First live result

Following the active manager's contract to Hungerford Town's first-team record
returned 17 player slots. The Phase 00 probe now publishes a deliberately small
projection for each supported player: stable ID, display name, date of birth,
age, position codes, display-precision condition and match fitness,
injury/suspension state, and bounded contract context. If no position meets the
accomplished/natural threshold, it reports the strongest position so a valid
player is not rendered positionless.

The contract team also distinguishes a loan correctly in the live sample:
Adam Siviter is in Hungerford's first-team collection while his contracted club
is Birmingham City. FM's 1900 contract-end sentinel is serialized as `null`,
not as a real date. Framework squad-status codes without a documented meaning
are also serialized as `null` rather than guessed.

The raw familiarity, condition, and fitness values are not serialized: fitness
values are rounded to the whole percentages shown to a manager. Current
Ability, Potential Ability, and other hidden attributes are not read into the
result. Per-player morale remains absent because this framework does not supply
a trustworthy mapping. A failure in an optional basic field produces `null` or
`unknown` without dropping an otherwise valid squad identity. The next manual
check is to compare the 17 identities and displayed values with the in-game
first-team squad screen, including loans, youth promotions, and a future
positive injury/suspension example.

FMBridge validates duplicate IDs, non-empty positions, ISO dates, and visible
percentages before serialization. The Python domain layer independently checks
percentage ranges. The sample fixture uses invented people and identifiers but
exercises the same public shape, including a loan and nullable values.

The response has been reproduced with the same 17 unique IDs after a clean
FMBridge restart. Current Ability, Potential Ability, personality internals,
raw fitness precision, and undocumented numeric squad-status values do not
cross the boundary. Playing attributes remain deferred until Phase 03 can prove
that the extracted representation is manager-visible; returning hidden truth
in Phase 00 would violate the project's principal constraint.

## Exit criteria

- Membership and identity match the in-game first-team view for the test cases.
- Duplicate and missing IDs are detected before serialization.
- A squad change appears on a later request.
- Every returned field has a recorded source and visibility justification.
