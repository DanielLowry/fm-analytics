# 00.2 — Process attachment

## Goal

Find and attach to the intended FM20 process without writing to it, and expose
attachment state without bringing down the HTTP service.

## Work

1. Wrap framework-specific discovery and attachment behind `IFmDataSource`.
2. Define states for game absent, process found, save not loaded, attached, and
   incompatible game build.
3. Decide how multiple candidate processes are handled; ambiguity must be
   surfaced rather than guessed away.
4. Verify whether attachment resources need deterministic disposal.
5. Add bounded retries or reattachment after FM restarts.
6. Add structured bridge errors with safe diagnostic context.
7. Check that every invoked framework operation is read-only.

## Scenarios

| Scenario | Expected behaviour |
| --- | --- |
| FM20 not running | Health reports unavailable; bridge stays alive |
| FM20 at main menu | Process is visible, game state is not ready |
| Save loaded | Source becomes ready |
| FM20 exits | Source returns to unavailable without stale data |
| FM20 restarts | A later request can reattach |
| Wrong executable version | Explicit incompatible-version result |

## Exit criteria

- The state transitions above have been observed and recorded.
- HTTP requests are bounded; attachment cannot hang them indefinitely.
- Logs contain no raw memory dumps or hidden player data.
- A process restart does not require restarting the bridge in the normal case.

## Linux/Proton finding

The Codex sandbox has its own PID namespace, so an in-sandbox process listing
cannot see FM20. A host-side process listing identified the Proton-hosted game
as a Linux process whose command line ends in `Football Manager 2020/fm.exe`.
The reusable `tools/fm20_linux_probe.py` identifies it from the executable
mapping rather than the mutable Linux process name (`Main Thread` was observed).

Direct read-only access to its `/proc/<pid>/mem` succeeded. The live
`LinuxProtonFmDataSource` now runs that probe behind `IFmDataSource`; running
the bridge inside Wine is not necessary.

Every request has a configurable ten-second probe timeout. Successful results
are cached for one second so `/game` and `/squad` form a near-simultaneous
observation, while failures are not cached and can recover on the next request.
The bridge distinguishes `game_absent`, `save_not_loaded`,
`ambiguous_process`, `permission_denied`, `incompatible_build`, timeout,
misconfiguration, and invalid payloads.

An isolated lifecycle run kept one bridge process alive while its test source
changed from absent to ready and back to absent. `/health` changed from HTTP
503 `game_absent`, to HTTP 200 `ready`, then back to HTTP 503. A separate
main-menu simulation returned HTTP 503 `save_not_loaded`. The live bridge also
reattached after a clean bridge restart and reproduced all 17 player IDs.

Actual FM-process exit and restart is deliberately not forced by automated
tests because it would close the user's game. The adapter performs process
discovery afresh after the one-second success cache, so no process handle or
pointer survives between probe invocations.
