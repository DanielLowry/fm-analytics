# 00.5 — End-to-end validation

## Goal

Demonstrate the complete live path and preserve enough evidence to keep it
working.

## Validation run

1. Start FMBridge before FM20 and observe the unavailable state.
2. Start FM20, load the documented test save, and observe attachment.
3. Query `/health`, `/game`, and `/squad` and retain sanitized responses.
4. Run the Python CLI against the bridge.
5. Advance the game, change first-team membership, and repeat the queries.
6. Restart FM20 and confirm reattachment.
7. Restart all components and repeat the happy path.

## Evidence

- Commands used
- Sanitized example responses
- Expected versus actual squad counts and selected identities
- Timings for cold attachment and ordinary requests
- Framework/game versions
- Known failure cases and recovery behaviour

## Recorded run

On 10 September 2026:

- `GET /health` returned `ready` from `linux-proton`.
- `GET /game` returned the expected active manager, Hungerford Town, and
  `2019-06-24`.
- `GET /squad` returned 17 unique first-team IDs and the approved field set.
- `uv run fm-analytics --base-url http://127.0.0.1:5072` printed all 17 live
  players through HTTP.
- A clean FMBridge restart reproduced the manager, club, date, count, and
  sorted player IDs.
- A cold live health request completed in about 0.25 seconds; the immediately
  following cached game and squad requests each completed in under 1 ms.
- Isolated source-state checks produced distinct `game_absent` and
  `save_not_loaded` responses and proved unavailable → ready → unavailable
  recovery without restarting the bridge.
- The exact Release build used by CI completed with zero warnings/errors, and
  all 34 Python tests passed.

- The live Python output satisfies the Phase 00 outcome.
- Failures are diagnosable without a debugger.
- A repeat run succeeds from documented instructions.
- Remaining visibility uncertainty is written down for Phase 03 rather than
