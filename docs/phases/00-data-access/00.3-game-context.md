# 00.3 — Game context

## Goal

Read the smallest live facts that prove the correct save and human manager have
been identified.

## Fields

- Current in-game date
- Human-manager stable identifier and display name
- Human-controlled club stable identifier and display name
- Optional source revision/build metadata for diagnostics, kept outside domain
  entities

## Work

1. Locate these values through the extraction framework.
2. Map framework objects into existing `GameState` DTOs.
3. Verify values visually against the loaded save.
4. Advance at least one in-game day and query again.
5. Reload the save and determine whether identifiers remain stable.
6. Test a manager between jobs and document the representation if supported.
7. Capture malformed/stale-pointer conditions as unavailable source errors.

## Exit criteria

- `/game` agrees with the FM interface in the test save.
- Date changes are visible without restarting the bridge.
- Identity behaviour across save reloads is documented.
- Absence of a controlled club is representable and does not masquerade as an
  extraction failure.

## First live result

The final FM20 framework definition records current date at module-relative
offset `0x7386EE0`. A four-byte read from the running process returned
`af 1a e3 07`: after applying FM's day mask and little-endian year encoding,
this is **2019-06-24**.

The checked-in Linux probe reproduces that limited read:

```bash
python3 tools/fm20_linux_probe.py
```

This proves process discovery, mapped-module discovery, and extraction of one
live game field.

A subsequent targeted traversal initially selected an inactive human-manager
object named `(Dan)`. FM retains this object alongside the live manager, so
using the first matching person record is not sufficient. The framework's
`ActiveObject` field initially matched **Dan Lowry** (ID `1915435127`), whose
contract resolves **Hungerford Town** (ID `5103652`). A later read showed that
`ActiveObject` can change while the save remains loaded, so it is now only a
selection hint. For a single-manager save, the unique human manager with a
managed-club/team contract is the stable fallback. Multiple managed humans are
rejected as ambiguous unless the hint disambiguates them.

The failed club-name read also exposed two FM string layouts: club names point
directly to their encoded string, while the tested person-name fields have an
additional indirection. The probe now handles these explicitly rather than
assuming one universal layout.

Saving the game is not required for these reads because they come from the
running process. A fresh save remains useful as a repeatable checkpoint for
reload and identifier-stability tests.

The live result now crosses the intended boundary:

```text
FM20 process -> LinuxProtonFmDataSource -> GET /game -> BridgeClient
```

The controlled club is nullable in both the C# and Python contracts, so a
manager between jobs is representable. The implementation rejects zero or
multiple active human managers as `save_not_ready` instead of selecting one
arbitrarily.

After a real FM process shutdown and restart, loading the same save reproduced
the manager ID, club ID, and `2019-06-24` date exactly. This establishes reload
identity behaviour for the Phase 00 save.

The save was not deliberately advanced at the user's preference. Because each
uncached read launches a fresh probe and retains no FM pointer, that scenario
is no longer a feasibility blocker; a live advancement soak check is recorded
in Phase 01.
