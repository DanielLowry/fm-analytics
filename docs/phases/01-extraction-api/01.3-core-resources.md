# 01.3 — Core resources

## Goal

Expose only resources with a demonstrated near-term consumer.

## Candidate sequence

1. `/health` and source status
2. `/game`
3. `/squad`
4. `/players/{id}` for a player already established as visible
5. `/clubs/{id}` for known clubs
6. A paginated discoverable-player/search resource only after Phase 03 proves
   its manager-knowledge source and inclusion rules
7. `/fixtures` for the controlled club when a current consumer requires it
8. `/competitions/{id}` only when fixture semantics require it

Each endpoint addition requires:

- a Python use case;
- an allowlisted DTO;
- visibility classification for every field;
- a sanitized contract fixture;
- missing/stale entity behaviour;
- ordering and collection-size decisions.

The existence of a raw player object or ID is not sufficient authorization for
`/players/{id}` or collection membership. Requests must not be usable to probe
the hidden database one ID at a time.

## Exit criteria

- `/game`, `/squad`, and the Phase 02 ingestion resources are sufficient for
  their documented consumers.
- Unused speculative fields and endpoints are absent.
- Entity relationships use stable IDs and do not require nested object graphs.
- The Phase 03 extension point for a discoverable-player collection has defined
  pagination, consistency, and forbidden-ID behaviour without prematurely
  exposing that collection.
