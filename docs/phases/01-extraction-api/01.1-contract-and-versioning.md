# 01.1 — Contract and versioning

## Goal

Make the JSON boundary boring, explicit, and changeable without coupling
Python to FM-specific implementation details.

## Work

1. Inventory the minimum resource shapes required by the Phase 01–06 MVP while
   implementing only those whose visibility semantics are currently proven.
2. Publish a machine-readable schema or equivalent golden-contract fixtures.
3. Choose an API version mechanism before the first incompatible change.
4. Specify ID, date/time, enum, nullability, units, pagination, and ordering
   conventions.
5. Define the error envelope and stable machine-readable error codes.
6. Distinguish missing, unknown, not applicable, and temporarily unavailable.
7. Specify additive versus breaking changes and the supported client window.

## Initial decisions to preserve

- External IDs are strings until extraction semantics prove otherwise.
- Dates use ISO 8601.
- Attributes are visibility-aware observations.
- Positions are raw normalized labels; tactical interpretation stays in Python.
- Framework object graphs are never serialized directly.
- Collection contracts support deterministic ordering, bounded pagination, and
  coherent capture identity before a discoverable-player collection is added.

## Implemented first slice

Contract v1 uses a major-version URL prefix (`/v1`) and returns its version in
the `X-FM-Analytics-Contract-Version` response header. Phase 00's unversioned
resource paths remain temporary v1 aliases. The Python client uses only the
versioned paths, and unsupported numeric majors return a stable error.

The current field, nullability, unit, ordering, compatibility, and error rules
are published in [the v1 contract](../../contracts/v1.md). The sanitized fixture
bundle identifies itself as v1 and is shared by endpoint and client tests.

The golden test exposed and closed an initial mismatch: attribute validation
forbade irrelevant numeric members, but serialization emitted those members as
`null`. V1 now emits only the members legal for its `known`, `range`, or
`unknown` tagged shape.

The client now wraps malformed resources in `BridgeContractError`, identifies
the resource and missing field where possible, validates required and nullable
types without coercion, accepts documented open strings, and rejects unknown
closed visibility tags. Golden cases cover the current resources, stable route
errors, degraded health, and a deliberately breaking renamed game-date field.

The [MVP squad-input inventory](mvp-squad-inputs.md) reconciles v1 with the first
tactic and role use cases. Live playing attributes remain intentionally absent;
that is a visibility research dependency, not an unfinished v1 representation.

## Completion record

01.1 is complete. Its contract and tests establish the compatibility boundary;
01.2 now owns live lifecycle/soak evidence, while Phase 03 owns proof of the
manager-visible attribute source.

## Exit criteria

- A reviewer can identify every field's type and semantics without reading the
  live probe or bridge implementation.
- Python rejects structurally invalid responses with useful context.
- A breaking-change example demonstrates how the version policy works.
