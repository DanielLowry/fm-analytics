# 01.1 — Contract and versioning

## Goal

Make the JSON boundary boring, explicit, and changeable without coupling
Python to FM-specific implementation details.

## Work

1. Inventory the minimum resource shapes required through Phase 03.
2. Publish a machine-readable schema or equivalent golden-contract fixtures.
3. Choose an API version mechanism before the first incompatible change.
4. Specify ID, date/time, enum, nullability, units, pagination, and ordering
   conventions.
5. Define the error envelope and stable machine-readable error codes.
6. Distinguish missing, unknown, not applicable, and temporarily unavailable.
7. Specify additive versus breaking changes and the supported client window.

## Initial decisions to preserve

- External IDs are strings until extraction semantics prove otherwise.
- Dates use ISO 8601.
- Attributes are visibility-aware observations.
- Positions are raw normalized labels; tactical interpretation stays in Python.
- Framework object graphs are never serialized directly.

## Exit criteria

- A reviewer can identify every field's type and semantics without reading C#.
- Python rejects structurally invalid responses with useful context.
- A breaking-change example demonstrates how the version policy works.
