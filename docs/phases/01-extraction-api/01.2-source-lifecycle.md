# 01.2 — Data-source lifecycle

## Goal

Make fixture and live sources interchangeable while handling FM's changing
process and save state correctly.

## Work

1. Evolve `IFmDataSource` only from observed use cases.
2. Keep framework-specific code in a dedicated implementation/assembly area.
3. Model discovery, attachment, readiness, detachment, and incompatibility.
4. Decide whether a request reads one consistent snapshot or may span game
   state changes.
5. Reacquire invalidated objects according to Phase 00 findings.
6. Add cancellation and time bounds around memory-reader calls.
7. Keep the fixture source deterministic and capable of representative errors.
8. While FMBridge remains running, advance the live save and make a temporary
   first-team membership change; confirm later uncached observations update.

## Exit criteria

- Switching source is configuration, not code modification.
- Source state transitions are covered by tests where they can be simulated.
- A request never mixes entities from two distinguishable in-game dates.
- Resource ownership and disposal behaviour are documented.

## Current evidence

Automated adapter tests now prove that a successful probe document is reused
only inside the one-second cache window, a later uncached request observes an
updated in-game date and squad membership, and a failed probe is not cached and
can recover on the next request.

The actual FM20 process was not running for this implementation pass. The
remaining live check is to keep FMBridge running, advance the save, temporarily
change first-team membership, and confirm later uncached v1 observations update
without restarting the bridge.
