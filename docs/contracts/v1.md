# FMBridge HTTP contract v1

## Versioning and compatibility

The canonical v1 resources are:

```text
GET /v1/health
GET /v1/game
GET /v1/squad
```

Every response includes:

```text
X-FM-Analytics-Contract-Version: 1
```

The contract major is part of the URL. An incompatible representation or
semantic change requires a new major prefix. New optional fields, new resources,
and new values for explicitly open string fields may be added within v1. A v1
client must ignore object fields it does not consume, but must continue to
reject invalid values for closed tagged unions such as attribute visibility.

Phase 00's unversioned `/health`, `/game`, and `/squad` paths remain temporary
aliases for v1. New consumers must use `/v1`. The aliases may be removed when a
future major is introduced, with release notes and a tested migration path.
There is no previous-major support promise while v1 is the only released major;
before v2, the supported server/client window must be decided from actual local
upgrade behavior.

Requests for another numeric major, such as `/v2/game`, return the
`unsupported_contract_version` error defined below.

## Common conventions

- Bodies are UTF-8 JSON objects and use `camelCase` property names.
- Entity identifiers are required opaque strings. Consumers must not parse,
  order, or perform arithmetic on them.
- Dates are `YYYY-MM-DD` ISO 8601 calendar dates in the FM save, with no implied
  wall-clock timezone.
- Optional or inapplicable scalar relationships use JSON `null`; required keys
  are not silently omitted.
- Percentages are visible whole-number integers from 0 through 100 or `null`.
- `visibility` is a closed discriminator. Availability, contract, squad, and
  transfer status strings are open pending a verified FM20 vocabulary.
- Array order is not a quality ranking. `squad.players` currently preserves the
  source squad order; consumers use player IDs for identity.
- Future unbounded collections must define deterministic ordering, a bounded
  page size, an opaque continuation cursor, and coherent capture semantics
  before release.

The sanitized golden resource bundle is
[`src/fm_analytics/fixtures/sample-game.json`](../../src/fm_analytics/fixtures/sample-game.json).
Its top-level `contractVersion` identifies which contract its `health`, `game`,
`squad`, error, and deliberately breaking example documents represent. Producer
and consumer tests read the same bundle.

## `GET /v1/health`

| Field | Type | Meaning |
| --- | --- | --- |
| `status` | string | Open operational state; `ready` is the successful state |
| `source` | string | Configured bridge source name |
| `detail` | string or null | Safe human-readable degraded-state context |

A ready source returns HTTP 200. An expected degraded source state returns HTTP
503 with the same health shape so health consumers can still decode it. The
detail must not contain raw memory or hidden player data.

## `GET /v1/game`

| Field | Type | Meaning |
| --- | --- | --- |
| `gameDate` | date | Current in-game date |
| `humanManager` | manager | The active human manager |
| `controlledClub` | club or null | The club controlled by that manager |

A manager contains required string `id` and `name` fields. A club contains
required string `id` and `name` fields.

## `GET /v1/squad`

| Field | Type | Meaning |
| --- | --- | --- |
| `club` | club or null | Controlled club associated with the collection |
| `asOfDate` | date | In-game effective date for the squad observation |
| `players` | array of player | First-team squad in source display order |

### Player

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | string | Stable-within-save opaque player identity |
| `name` | string | Manager-visible display name |
| `dateOfBirth` | date or null | Visible birth date |
| `age` | non-negative integer or null | Visible age on the observation date |
| `positions` | non-empty array of string | Visible normalized FM position labels |
| `clubId` | string | Squad club identity; contract ownership is separate |
| `conditionPercent` | percentage or null | Manager-visible whole-number condition |
| `matchFitnessPercent` | percentage or null | Manager-visible whole-number sharpness/fitness |
| `availability` | string | Open selection-availability state |
| `injured` | boolean or null | Visible injury status when established |
| `suspended` | boolean or null | Visible suspension status when established |
| `contract` | contract or null | Visible contract observation when established |
| `attributes` | object | Attribute name to observation mapping |

Current condition, match fitness, availability, and intrinsic attributes remain
separate observations. Consumers must not interpret absent live attribute
mappings as zero ability.

### Contract

| Field | Type |
| --- | --- |
| `contractType` | string or null |
| `startDate` | date or null |
| `endDate` | date or null |
| `joinedDate` | date or null |
| `squadStatus` | string or null |
| `transferStatus` | string or null |
| `contractedClub` | club or null |

Contract fields are observations, not guarantees of attainability or cost.

### Attribute observation

An attribute value is exactly one of these tagged shapes:

```json
{ "visibility": "known", "value": 15 }
{ "visibility": "range", "minimum": 10, "maximum": 14 }
{ "visibility": "unknown" }
```

- `known` requires `value` and forbids `minimum` and `maximum`.
- `range` requires an inclusive `minimum` and `maximum`, with minimum no greater
  than maximum, and forbids `value`.
- `unknown` forbids all numeric value fields.

The live bridge must construct these shapes from approved manager-knowledge
sources. Reading a hidden exact value and discarding it later is not compliant.
Unavailable and stale observations require an additive surrounding metadata
design before they are emitted; they are not silently aliases for `unknown`.

## Error envelope

Except for the intentionally decodable degraded `/health` document, an error is
a JSON object containing:

| Field | Type | Meaning |
| --- | --- | --- |
| `status` | string | Stable machine-readable error code |
| `error` | string | Safe human-readable explanation |

Source failures currently include `game_absent`, `save_not_loaded`,
`ambiguous_process`, `permission_denied`, `incompatible_build`, `timeout`,
`invalid_payload`, `misconfigured`, and `unavailable`. Routing additionally uses
`not_found` and `unsupported_contract_version`.

Error text is diagnostic, not a stable parsing surface. Errors and status codes
must not reveal hidden field values, hidden player existence, raw memory, or
framework object details.
