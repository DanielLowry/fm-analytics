# UI review and finishing checklist — 30 September 2026

## Status and scope

**Status: partial implementation delivered on 2 October 2026; see the implementation record below. Broad acceptance items remain open pending the complete state matrix.** The
TailAdmin-inspired shell is a useful foundation, but implementation of the
shell is not the same as completed visual and interaction acceptance. The
earlier description of the UI refactor as entirely complete was too strong.

This records the final browser review and its recommendations, not completed
fixes or permission to start every item. The [active plan](active-plan.md)
remains the source of delivery priority. Priorities here order the UI work
relative to itself; they do not reschedule recruitment, analytics or research.

Keep the current green/navy identity, sidebar grouping and TailAdmin-inspired
direction. The proposed work improves readability, information hierarchy and
continuity within the existing app. It does not require another template,
a framework migration or changes to football scoring.

## Evidence and limitations

The review used a local preview of the current application with saved data,
not an attached live FM session. It covered 13 main/list/detail screens in
light and dark themes at 1440 × 1000, with selected mobile journeys at
390 × 844 and an additional match-detail check:

- Command centre, Squad and squad player report;
- Roles, Depth, Tactics and tactic detail;
- Set pieces, Matches and match detail;
- Tactic checks, Data health, Scouting and scouting player report.

The preview used a 17-player saved squad, 4,631 scouting candidates and saved
match history. The older squad capture was adapted read-only for this
disposable preview; that is not a supported production migration or a change
to the application's refusal of pre-baseline capture schemas. Match history
was copied to temporary storage. Preview pins exercised tactic layouts and
were not an assertion about the manager's current selected tactics.

The captures have different game dates. Findings below concern presentation
and interaction, not the correctness of cross-capture football conclusions.
Page measurements are examples from that dataset and viewport, not universal
page sizes or performance benchmarks. Temporary screenshots are not durable
repository dependencies; reproduction steps and observations are recorded
here instead. No refresh, capture or verdict actions were submitted, and no
application code was changed during the review.

### UI-01 — Complete dark-theme readability

**Observed.** The Tactics opponent-profile panel has pale text on a pale
background. Set-piece taker names are nearly black on dark cards. Dashboard
metric labels and explanatory text are dim, as are some player-report links,
fact labels and form labels. Some inputs retain white surfaces. Tactic-detail
headline scores and some match-detail descriptions also need checking.

**Proposed change.** Define shared semantic colours for primary/muted text,
surfaces, borders, links, controls, focus and status states in both themes.
Use those throughout shared components and remove competing legacy colours
as each component migrates. The current dark root changes surface tokens but
leaves many light-theme ink colours intact; local overrides are incomplete.

**Acceptance.**

- [ ] Every reviewed route is readable in both themes, including nested
  panels, tables, forms, links, warnings and expanded details.
- [ ] Normal text meets a 4.5:1 contrast target; large text and meaningful
  control boundaries/focus indicators meet a 3:1 target where applicable.
- [ ] Theme changes, reloads, hover, focus, disabled and loading states do not
  reintroduce mismatched foregrounds and backgrounds.

Start in [frontend styles](../frontend/styles/app.css),
[shared rendering](../src/fm_analytics/web/rendering.py) and
[opponent controls](../src/fm_analytics/web/opponent_controls.py).

### UI-02 — Contain mobile overflow

**Observed.** At a 390-pixel viewport, both player-report variants expanded
the document to about 988 pixels. Matches also overflowed, to about 456
pixels. The player-report issue cuts off whole panels, not just wide tables.

**Proposed change.** Correct grid/flex minimum sizing and contain wide tables
inside labelled horizontal-scroll regions. Stack report facts and controls
at small widths; do not conceal the defect with page-level overflow clipping.

**Acceptance.**

- [ ] No unintended page-wide horizontal scrolling at 320, 390, 768 or 1440
  pixels, including player and match detail pages.
- [ ] Wide tables scroll internally without losing surrounding headings,
  actions or text; all columns remain reachable.
- [ ] Long names, clubs, roles and expanded sections remain usable in both
  themes and at increased text size.

Start in the frontend styles and
[player-report renderer](../src/fm_analytics/web/scouting_report.py).

### UI-03 — Correct mobile navigation keyboard behaviour

**Observed.** On mobile with the sidebar closed, pressing Tab focuses the
off-screen brand and navigation links. The drawer is moved off-screen but
its contents remain keyboard-reachable.

**Proposed change.** Make the closed drawer genuinely inactive, manage focus
while the overlay drawer is open, restore focus to its trigger when closed,
and provide a skip-to-content link. Keep desktop navigation accessible when
crossing the responsive breakpoint.

**Acceptance.**

- [ ] Closed-drawer links cannot receive focus; opening moves focus inside.
- [ ] Escape, the close button and overlay dismissal restore useful focus.
- [ ] Keyboard focus remains within the open modal drawer and is visible.
- [ ] Accessible names/expanded state, skip navigation and desktop/mobile
  resizing work without stranding focus or disabling desktop links.

Start in [shell JavaScript](../frontend/scripts/app.js) and the
[base template](../src/fm_analytics/web/templates/base.html).

### UI-04 — Synchronise Scouting state and preserve return context

**Reproduced.** Open `/scouting?position=ST&includeRawPositions=1`, then change
the position to DC. The URL and results heading update to DC, while the
Current focus card still says ST. The live response replaces the results
region, not the summary outside it.

Open a player from that filtered All players list. The report's return link
is always `/scouting?view=scouted`, losing the original tab and filters.

**Proposed change.** Keep the summary, tabs, filters, result heading and URL
in agreement. Carry safe local return context into reports, preserving the
view, query, sort, limit and scroll position. Cover browser Back/Forward and
reload as well as the explicit return action. Tab URLs and request ordering
need regression checks, not just the confirmed summary bug.

**Acceptance.**

- [ ] Position, role and tactic changes update every visible state indicator.
- [ ] Filter → open player → return restores the same list and position for
  both All players and Scouted; direct report visits have a sensible fallback.
- [ ] Reload, Back/Forward, rapid filter changes and failed requests do not
  leave contradictory controls, headings or results.
- [ ] Return targets cannot navigate to arbitrary external URLs.

Start in [Scouting pages](../src/fm_analytics/web/scouting_pages.py),
[live-filter script](../src/fm_analytics/web/scouting_script.py),
[result links](../src/fm_analytics/web/scouting_render.py) and the player-report
renderer. Preserve the existing scouting-state regression coverage.

### UI-05 — Put results and recommendations first

**Observed.** Populated Scouting results began around 1,694 pixels down on
desktop and 3,036 on mobile. Introductory copy, summary cards, a separate
capture panel, weakest slots and filters all precede the table. Active view
and Current focus repeat information already conveyed by tabs and controls.
On Tactics, a large opponent-profile editor precedes recommendations; the
first table began around 1,050 pixels down in the reviewed desktop layout.

**Proposed change.** Use a compact Scouting heading with capture freshness and
Refresh, followed by view tabs, essential filters and results. Make weakest
slots, advanced filters and scoring explanations expandable, retaining the
one-click links from squad needs to candidate searches. Make the opponent
editor collapsible with a visible summary of active assumptions.

**Acceptance.**

- [ ] Results/recommendations follow primary controls without requiring users
  to traverse introductory, capture and optional analysis panels.
- [ ] Large duplicate state cards are removed or replaced by compact context.
- [ ] Freshness, active filters, important warnings and uncertainty remain
  visible; optional panels do not hide information needed to interpret scores.
- [ ] Before/after desktop and mobile screenshots show the reduced distance
  to the main task; all existing filters and refresh actions remain available.

### UI-06 — Make player reports progressive

**Observed.** The reviewed squad and scouting reports were approximately
11,300–11,400 pixels tall on desktop because role rankings for every position
are expanded. This obscures the player's relevant strengths and next action.

**Proposed change.** Introduce Overview / Attributes / Role fit / History
sections using accessible tabs or section navigation. Lead with key facts,
best relevant roles and the scouting decision where applicable. Show relevant
positions first and make exhaustive rankings an explicit All roles/details
choice. Preserve direct section links and accessible expanded content.

**Acceptance.**

- [ ] Initial view answers who the player is, where he fits and what evidence
  supports that view without requiring exhaustive-table scrolling.
- [ ] Every existing attribute, role score and history detail remains reachable.
- [ ] Historical dates, unknowns, estimates and manual verdict semantics remain
  explicit; an overview must not imply that incomplete data is certain.
- [ ] Navigation and section state work on desktop, mobile and keyboard in
  both report variants; return context follows UI-04.

### UI-07 — Separate Matches overview, results and analysis

**Observed.** The Matches page was about 8,000 pixels tall on desktop, with
the first table around 2,295 pixels down. Multiple useful analyses compete
for space in one long page.

**Proposed change.** Provide clear Overview / Matches / Analysis views, or
equivalent section navigation with expandable detailed diagnostics. Keep
important current findings prominent without requiring the full diagnostics
explanation before the match list.

**Acceptance.**

- [ ] Recent matches and key findings are easy to reach independently.
- [ ] Detailed diagnostics, trends, filters and match drill-downs remain
  available with meaningful headings and preserved navigation context.
- [ ] No analytics are removed or recomputed in the presentation layer.

Start in [match pages](../src/fm_analytics/web/match_pages.py) and
[match rendering](../src/fm_analytics/web/match_render.py).

### UI-08 — Connect screens with contextual navigation

**Observed/recommended.** The shell's breadcrumb is a section label rather
than a clickable path. Roles contains player names that are not report links.
The useful journey from a depth concern to candidates can be made more direct.

**Proposed change.** Add clickable trails such as Scouting → Player and
Tactics → Tactic, consistent back actions, player links across Roles/Depth/
Squad where a report exists, and depth-to-filtered-scouting links. Consider
placing Tactic checks under an advanced/reference area within Tactics so
everyday navigation gives less prominence to diagnostic tools.

**Acceptance.**

- [ ] Review gap → find candidates → inspect player → return is a connected
  journey with the tactic/position/role and list context preserved.
- [ ] Breadcrumb parents and repeated player links lead to consistent targets.
- [ ] Active sidebar state remains correct on detail pages; diagnostic tools
  remain discoverable if relocated.

### UI-09 — Standardise visual components and copy

**Observed/recommended.** Mixed text-symbol icons, differing button/form
treatments, repeated introductory copy and oversized cards weaken consistency.

**Proposed change.** Use one consistent SVG icon family and shared primary/
secondary/destructive button treatments, field heights, heading levels,
spacing, radii and focus states. Establish a clear typography scale and
intentional font loading/fallback. Reserve large cards for meaningful groups
or decisions; make secondary explanations compact. Prefer plain football
language, with technical explanations available on demand.

**Acceptance.**

- [ ] Equivalent controls look and behave alike across all reviewed screens.
- [ ] Icon size/weight, heading hierarchy and spacing are consistent in both
  themes, including expanded and empty states.
- [ ] Copy is concise without concealing provenance, uncertainty, missing
  evidence or diagnostic limitations.

### UI-10 — Improve tables and interaction feedback

**Observed/recommended.** The populated Scouting table needed about 1,848
pixels within a roughly 1,073-pixel desktop container. Long position and role
lists create tall rows. Large tables are harder to scan when headers and
player identity disappear during scrolling.

**Proposed change.** Align comparable numeric columns consistently, use
tabular numerals, shorten repetitive labels, and move secondary details out
of default columns where appropriate. Keep table headings and player-name
columns visible during the relevant scroll direction. Use consistent busy,
success and error feedback without unnecessary layout jumps or loss of focus.

**Acceptance.**

- [ ] Scores, money and other numeric columns scan cleanly; full names and
  role meanings remain accessible when labels are shortened.
- [ ] Sticky headings/identity columns work inside the actual scroll
  containers without overlapping content, the topbar or keyboard focus.
- [ ] Mobile users can reach all data, with useful core columns visible first.
- [ ] Filtering/refresh feedback is visible and announced accessibly; errors
  retain usable context and controls. This does not authorise the separately
  parked background-refresh or cache-rework projects.

## Suggested implementation sequence

1. UI-01–UI-04: correct theme, responsive layout, keyboard and state defects.
   Establish shared components while correcting them.
2. UI-05–UI-07: simplify Scouting, player reports and Matches around their
   primary tasks, retaining full evidence behind secondary views.
3. UI-08–UI-10: complete cross-screen navigation, component consistency,
   dense-table behaviour and interaction feedback.
4. Repeat browser acceptance across the full route/theme matrix before
   calling the UI refactor finished.

This order is a recommendation, not a scheduled implementation commitment.
Coordinate Scouting changes with active-plan items 2–3 so the forthcoming
My tactics and Trial priority views reuse the same controls and layout.
Do not un-park dashboard analytics, named depth evidence, caching or
background jobs merely to complete presentation work.

## Implementation record — 2 October 2026

Delivered the shared table and information-density changes requested after
this review:

- All rendered data tables use the shared browser table controls: immediate
  search, row count, reset and keyboard column sorting. Numeric sort values
  and missing values are handled explicitly. Starting-XI explanation rows
  travel with their player when sorting and filtering.
- Scouting loads the complete server-scored candidate snapshot for the current
  scoring context. Ordinary filters and sorts then run locally, including
  candidates outside the visible rows. Position/role/tactic/raw-policy changes
  still obtain new server scores; the latest four contexts are cached for the
  visit. GET rendering remains the no-JavaScript fallback.
- Squad rosters, Depth, position choices, report tables, role coverage and XI
  slots use the goalkeeper-to-striker, left-to-right convention. Rankings by
  score retain their scoring order; position lists within a cell follow pitch
  order.
- Scouting results precede optional squad needs and alerts. Capture controls
  and the Tactics opponent editor are collapsible. Matches precede detailed
  analysis. Player reports expose section navigation, concise profile facts,
  and collapsible attributes, familiarity, history and per-position role lists.
- Table descriptions use concise summaries with full bullet-point evidence on
  demand. Score cells lead with the number; role duty and familiarity details
  remain accessible. Unknown familiarity remains labelled in the visible cell.
  Scouting attributes link directly to the report section, retaining visible
  counts, unknown/capture state and historical notices.
- Dark ink/surface tokens and legacy panel overrides cover inputs, opponent
  controls, instruction cards, set-piece names and charts. Mobile table overflow
  stays inside the table container. Closed mobile navigation is inert, supports
  focus restoration/trapping, and has a skip-to-content link.
- Scouting report return links preserve safe local list context. Filter group
  counts, tab links and sort direction follow the active controls.

## 3 October 2026 — dependent squad filters

Squad now embeds the full catalogue of position-compatible roles. Its role
selector updates immediately when the position changes, keeps a compatible
selection and clears an incompatible one. Roles are disabled until a position
is selected. Squad and Scouting share the same catalogue mapping and browser
selector logic. Squad Compare remains an explicit server-scored GET request.

Verification used a complete 11-player test squad and scouting state fixtures,
without a live FM session. All 14 position menus updated synchronously with
zero requests (at most 0.2 ms in this local Chrome run); pinned-role submissions,
Scouting dependencies, and the dark mobile squad layout were also checked.
The focused UI, server and position-comparison suite passed 32 tests. A browser
pass covered the command centre, Squad, Roles, Depth, Tactics and its detail,
Set pieces, Matches, Tactic checks, Data, and a scouting player report. The
Matches fixture was empty, so its populated filter behaviour was inspected in
the renderer rather than verified with captured match history.

Recommended next interaction work from this pass:

- Keep squad comparison and match-review results in place when applying their
  controls. The current Compare and Show flows still submit whole pages;
  retain server scoring and update every dependent summary alongside results.
- Reset Scouting filters locally while preserving the current tab and cached
  ranking snapshots. The existing Reset filters link reloads the page.
- Shorten comparison cells to one-line summaries, with familiarity assumptions,
  multipliers and detailed score explanations in expandable cells. The squad
  comparison still repeats that evidence in every player row.

### Other club squad estimates

The other-squad tables now display role-fit, in-position and available-today
scores using the same reporting helpers as the first-team roster. Names link
to the owned-player report, including every position estimate, attribute
evidence and role breakdown. These reports identify the captured squad marker
and return directly to the other-squad section. The comparison form offers
First team, each captured other squad, and All club squads; whole-club results
show squad membership. The first-team roster remains separately labelled.
Tactic and XI recommendation inputs continue to use the first-team players.

Regression coverage checks equal scores for identically captured players in
different squads, scoped comparison membership and ranking, report links,
empty squads, missing inputs, escaped names and exclusion from tactic plans.
Chrome checks used an 11-player first team, four other players across two
squads and an empty third squad. Position ordering, local filtering, copying,
comparison submission, report return links and dark mobile containment passed.
The squad, UI, scouting-report and position-comparison suites passed 81 tests;
web-module compilation and `git diff --check` also passed.
